# 基础状态与站起反馈修复

目标：导航、定位、建图均未启动时仍显示可读取的CPU、内存、电量和电机状态；收不到机器人反馈时显示未知，不能把指令完成当成实际站起。

已查证：电量/温度订阅的是域43的`/go2w/robot_lowstate`，由planar_odom转发，依赖导航/里程计进程。CPU本身来自/proc，但与整包导航状态共用推送路径，中间异常会跳过后续基础状态。运控FixStand.ready由插值计时置true，不核对实测关节。本次开始时的现场.21只读快照为v1.4.2、导航运行中，CPU83.5%、电量15%、控制Passive；只读取了HTTP和WS，没有改变档位或发送运动命令。SSH公钥认证未成功，未取得历史故障日志，不能把本地反例说成原故障已经复现。

实现边界：继续在独立克隆dhb/param_api开发。域0复用已有机器人通信节点，直接旁听原始/lowstate；GO2W_CTRL=0时只启用只读监听，不创建运动请求发布者。raw回调限频，不重复反序列化整包。基础状态单独推送，导航状态出错不阻塞CPU/电量。断线或数据过期清空旧值。

姿态依据运行控制配置中的FixStand最终12关节目标和可选的Passive软着陆目标；从实测关节和IMU核对，缺配置、无反馈、过期和全零反馈均不得确认为站起。站起流程等控制状态ready后还须等待连续新鲜实测关节到位，再启动策略；失败不进入下一阶段、不增加stood。配置目标从supervisor当前control进程的/proc/PID/cmdline读取实际--config，兼容独立运控发布，不给其他策略套用硬编码目标。角度容差0.45rad和连续实测确认窗口0.3s（相邻样本间隔不超过0.5s）是保守的软件验收条件，需在真机正常站起验收；不能当成接触地面或承重传感器。

复查与回归：静态目标仅用于站起确认，正常Velocity步态允许动态偏移；确认凭据绑定控制状态/序号、接收状态历史及反馈/配置代次。单帧后等时间、旧帧跨序号/配置、停流恢复、未轮询期间的趴姿/异常倾角均不能签发或复活旧凭据。异步读取配置后重新检查急停/互斥/取消，每次发送非趴下请求前再检查急停。现有示教准备夹具补齐真实低层反馈和climb初始值，继续使用产品站起实现验证取消边界。

验证证据：92项单元/协议回归通过；2项真实HTTP/WS无导航假ROS集成通过正常站起与FSM虚报失败、反馈中断后清空电量但CPU继续。Chrome通过无导航/无地图CPU内存和0%电量、虚报ready和成功ACK不替代姿态、站姿恢复、过期断线清理，并复现/修复了1440px状态卡片裁剪，改为自适应换行。独立审查的具体问题均已修复并经定向反例复查通过。一次将无导航与原路线集成合并运行的进程被SIGTERM（143）中断，未将其计为通过；最终原路线集成单独复跑通过（44.8秒），覆盖逐站/连续、取消、初始化失败和参数恢复门槛。

证据边界：尚未复现用户原来的低电历史故障，也未进行真机站起、动态步态或Orin资源占用验收；当前证明的是软件错误判断和边界处理已通过可重复本地测试。

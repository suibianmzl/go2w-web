# 网页控制台

替代 RViz 和 `nav.sh` 的网页界面。三栏布局：左边图层和 topic，中间地图，右边任务、运行档位、定位质量和底盘控制。

```
server/go2w_web.py   后端：rclpy 节点（域 43）+ aiohttp，HTTP 和 WebSocket 同一端口
server/procs.py      运行档位的进程管理（经运行容器 supervisor 的 socket 启停进程组）
server/camera.py     前置摄像头 RTP 组播接收、拼帧
server/cpu_stats.py  按需采集当前运行环境中占 CPU 最高的 5 个进程
server/mapmeta.py    地图续建：<name>.meta.json 读写、血缘、续建前置检查
server/mapcontinue.py 地图续建：起点位姿三级降级、图外检查、自检时的「还在起点吗」
server/teaching.py   每图唯一示教的文件仓储、持久采集与断点恢复
server/teaching_bridge.py 示教定位自检、精确时刻测量和HTTP/WS流程
tools/              随网页包部署的工具脚本（map_overlap_check.py 续建自检等；源在主仓库 scripts/calib）
static/              前端：原生 JS 模块，不需要构建
  js/source/mock.js  模拟数据源（示例地图 + 机器人仿真）
  js/source/ros.js   ROS 数据源（连后端 /ws）
dev/                 本地调试：假 ROS、假摄像头、协议测试
prototype/           最早的单文件原型和右栏原型，留作对照
```

界面只读 `js/store.js` 里的状态，两个数据源负责填它；操作统一经过 `js/actions.js` 做前置检查和确认。

## 和 go2w 主仓库的关系

这个仓库是从 [go2w](https://github.com/SinceJULY99/go2w) 的 `web/` 目录拆出来的（11-10，保留了历史）。代码本身单独维护，但运行时仍依赖主仓库：

- 11-12 起扩展坞跑的是统一运行容器 `go2w_runtime`（镜像 `go2w-runtime:<release>`，由 systemd 的 `go2w-runtime.service` 启动），不再有 `go2w_humble` / `go2w_web` 两个容器。网页打包在镜像里：后端 `/opt/go2w/console/server`，前端 `/opt/go2w/console/static`。
- 导航、巡逻、录包、回溯、速度桥都是容器里 supervisor 管的进程组，后端经 `/run/go2w/supervisor.sock`（环境变量 `GO2W_SUPERVISOR_SOCKET`）请求启停；运控 control 组和 DDS 录制不归网页管。
- 存图、对齐地图由后端直接起子进程，脚本在 `/opt/go2w/console/tools/`（`save_map.sh`、`align_map.py`）。
- 调整 Nav2 障碍物处理：`POST /api/obstacles-critic/true` 会将 `/controller_server` 的 `FollowPath.ObstaclesCritic.enabled` 和 `/global_costmap/global_costmap` 的 `voxel_layer.enabled` 都设为 `true`；`POST /api/obstacles-critic/false` 会将两者都设为 `false`。两个 ROS 参数依次设置，全部成功才返回成功，响应中的 `parameters` 列出两个节点、参数名、设置值及命令输出；执行失败、超时或 ROS 2 命令不可用时返回对应 HTTP 错误。部署进程的 PATH 需能找到 `ros2`，当前 ROS 2 环境需能访问上述节点。
- 数据目录是容器里的 `/go2w/data`（扩展坞上 `/opt/go2w/data`），可以用 `GO2W_DATA` 改。地图、路线、录包都在那里，不进这个仓库。导航日志在 `data/logs/navigation.log`，遥控速度桥在 `data/logs/bridge.log`。

## CPU 明细（v1.5.0）

点击顶部 **CPU** 框，弹窗按占用率从高到低显示最多 5 个模块/进程的名称、PID 和 CPU 占用率。首次采样约需 0.5 秒，之后在上次请求完成 2 秒后自动刷新；关闭弹窗后停止请求。进程名优先使用 ROS 节点重命名，否则显示脚本名或可执行文件名，不返回完整命令行。没有可统计的进程、读取失败或超时会显示提示，失败时清除旧榜单，恢复后重新显示。`?mock` 页面明确标为模拟数据。

占用率按整机所有 CPU 的总容量计算，同一进程的线程合计；例如 8 核机器上持续占满 1 核约为 12.5%。明细只覆盖网页后端所在 PID 命名空间可见的进程：正式运行容器中的导航、定位、运控、录包和网页进程可以统计，容器外进程不在列表中。同一进程中的 ROS 组件合并统计，前 5 项之和不代表整机总占用。排序使用未四舍五入的原始采样值，界面保留一位小数。

只读接口 `GET /api/system/cpu` 返回 `{ok,cpu,items:[{pid,name,cpu}],sampledAt,window,scope:"visible_processes",skipped}`；读取不可用时返回 HTTP 503 和 `ok:false`。后端在工作线程读取 `/proc`，多个客户端共享采样和 1 秒缓存，不加入导航指令队列或高频状态推送。需要同时更新前端和后端，并重启网页后端；通过反向代理访问时，须将 `/api/system/cpu` 转发到同一网页后端。旧后端返回 404 时，弹窗会提示更新。

本地验证（不连接机器狗）：`python -m unittest dev.test_cpu_stats -v` 检查多核口径、前 5 名、低占用排序、PID 重用/退出、缺失数据、HTTP 状态、并发缓存及取消。使用安装了 Playwright 的 Python 运行 `dev/test_cpu_details_browser.py`，验证点击、自动刷新、错误恢复、空数据/超时、关闭取消、快捷键隔离和保留 Space 急停、桌面及手机布局；`dev/test_route_force_crossing_integration.py` 另覆盖真实后端的 Linux CPU 采样和既有导航回归。

## 多点路线任务

**v1.4.0：站点限速。** 新建或编辑站点时可填写「最大 vx」（0.1–1.2 m/s），留空表示继承当前任务的最大 vx。每段实际限速取任务上限、起点限速和终点限速中的最小值；首次从当前位置接近第一站时，取任务和目标站点限速中的最小值。循环回到首站、断点续跑也采用相应站间限制。连续通过模式在限速变化处分段，其他同限速站点仍可连续通过；旧任务无需修改。任务最大 wz 现在可设置到 2 rad/s。

新版增加右上角 **示教采集**、中央实时采样和左侧示教图层，以及 `/taught-editor` 独立路线编辑页。每张地图的唯一活动示教直接保存到该地图 YAML；校验通过后，普通导航自动使用。暂停、断线续采、追加/局部替换、文件关系与本地测试见 [示教轨迹使用说明](docs/示教轨迹使用说明.md)。这与下面的多站导航任务是两个用途。

1. 加载地图，点击工具栏的「导航点」（快捷键 4）。单击地图添加一站，或在站点按住拖出箭头，松开后保存箭头指向的到站朝向。右侧按顺序列出站点，可以给每站填名字。每条路线可包含 2–50 个点。
2. 用箭头调整顺序或用 × 删除点。点「确认路线」后，最后一站标为终点，只对未手动指定朝向的站点按路线推算默认方向。确认会请求 Nav2 检查站间路径，在地图上画出规划结果。可以先保存未检查的路线。
3. 输入名称并点「保存任务」。任务绑定当前地图。从列表选中后可修改或删除任务。需要运行时，从列表选中任务，在对应地图启动导航、确认定位并解锁底盘，再点「启动导航任务」。按钮下方会说明暂时不能启动的原因。
4. 出发前后端用当前位姿补算第一段，并重新检查整条路线。任何一段规划失败都不会出发。通过检查后，每站用一次 Nav2 导航，成功到达才派发下一站。任务卡片显示当前站和总站数，执行中失败会停止。

5. **循环：** 启动前勾选「循环」并填圈数。1 → 2 → … → 终点 → 1 算一圈：到终点后直接回 1 号点，不原路返回。回到 1 号点时按它自己的朝向停（自动朝向 = 面向 2 号点）。2 圈就是走两遍，下一圈从 2 号点出发；0 圈表示一直循环，直到取消。出发前检查一整圈，包括终点回 1 号点那一段。不勾选就是单程，停在终点。圈数只在启动时生效，不存进任务。
6. **从 1 号点附近出发：** 启动时离 1 号点不到 0.5 m，就当已经在 1 号点，直接去 2 号点（太短的路径 Go2W 容易卡住不动）。

网页上的 A/B 往返巡逻和地图工具栏的「导航目标」已移除（11-06），用多站任务代替：两个点加「循环」就是往返巡逻。命令行（`nav.sh`）启动的 `patrol.py` 后端仍会识别：取消、急停、切换档位时会连它一起停，它运行时网页拒绝启动多站任务。多点任务执行时，其他网页不能另发单点、巡逻或键盘遥控指令。取消、急停、上锁、控制方心跳丢失、切换地图或运行档位都会结束整条任务。连接恢复后不会自动继续。路线存在后端的 `data/routes.json`，和地图一样可单独备份。纯前端 `?mock` 的路线存于当前浏览器，没有 Nav2 规划检查。假 ROS 后端会把规划结果明确标为「本地模拟」。真实规划预览只代表检查时的地图与代价地图，执行中仍由 Nav2 根据最新障碍物重规划。

本地可用 `dev/run.sh` 启动假机器人，再运行 `node dev/test_routes.mjs` 验证多点协议和停止行为。真机验收时要检查实际到点、朝向和停车。

## 右栏任务流程（11-06）

右栏顶上是三个任务：**导航 | 重定位 | 建图**。点标签就是真的切换档位，切换时一律先停车（取消任务、底盘上锁）。原型见 `prototype/right_panel.html`。

- **导航**：没在跑时弹框选地图、确认站立静止，确认后直接启动导航。之后按五步走：地图 → 初始位置（用「初始位姿」工具，或确认 AMCL 当前位置正确）→ 导航任务（只列当前地图的任务，新建 / 编辑沿用原来的路线编辑器）→ 运行参数（循环、最大 vx / wz）→ 启动。「启动导航」弹确认框列出这次的设置，确认后后端先解锁再出发（`route_start` 带 `arm: true`，出发失败会把锁再上回去）。
- **重定位**：导航在跑时不重启导航栈，只取消任务、上锁；导航没在跑时启动「定位」档位。在 AMCL 当前估计的基础上手动微调：方向键按屏幕方向平移、Q / E 旋转（步长 1 cm·0.5° / 5 cm·1° / 20 cm·5°），或在地图上拖青色机器人平移、拖车头圆点旋转。激光按修正后的位姿重画，贴墙绿、悬空红，匹配率在前端实时算（和后端一样，离墙 0.10 m 内算对上）。点「应用到 AMCL」才发出，用小协方差（σ 5 cm / 2°，`initial_pose` 带 `cov: "fine"`）。有没应用的改动时离开会先问。偏得太远时用「重新给位置」走普通初始位姿。
- **建图**：确认站立静止后停掉导航、启动建图。五步：建图中（运行时长）→ 遥控走一圈（可勾选同时录包）→ 地图对齐（可选，从底部抽屉挪过来）→ 保存地图（默认名 `lab_年月日`，后端不覆盖同名，保存后自动换成 `_2`、`_3`…）→ 结束：「用这张图去导航…」（弹框里默认选刚保存的图）或「停止建图」。没保存就离开会提醒。底部抽屉「地图与录包」只留地图列表和录包管理。
- 原来的「运行档位」卡片只在调试模式显示。

## 摄像头

地图区里的摄像头浮窗显示 Go2W 前置摄像头：地图右上角按钮列最下面的摄像头按钮打开 / 关闭（默认关着），标题栏 ✕ 关闭；拖标题栏移动，拖右下角按画面比例缩放，双击右下角恢复默认（左下角、宽 320 px）；位置和大小记在本机浏览器 `localStorage` 的 `go2w.camWin`。只在浮窗开着且浏览器标签页在前台时传画面。主控 `192.168.123.161` 在机器狗内网组播 `230.1.1.1:1720`，格式为 RTP/H.264，1280×720，约 14 帧/秒，约 1.5 Mbit/s，约每 2 秒一个关键帧（11-06 在扩展坞上实测）。后端在扩展坞有线口上接收，只把 RTP 拼回完整帧，不解码，再经 `/ws` 原样转发。浏览器用 `js/vendor/jmuxer.min.js`（jmuxer 2.0.7，MIT）封装成 MSE 播放，http 页面就能用。

- 只有这个标签页开着、底部面板展开、浏览器标签页在前台时才传输。切走后后端退出组播，不再收任何数据。
- 同一时间只给一个网页传画面。别人在看时显示对方 IP，可以点「接管画面」。
- 打开后最多约 2 秒出画面（要等下一个关键帧）。网络跟不上时，画面会跳到下一个关键帧，延迟不会越积越多。
- 拖高底部面板可以看大一点，面板高度会被记住。
- 后端的接收地址和网口可以用环境变量 `GO2W_CAM_ADDR`（默认 `230.1.1.1:1720`）和 `GO2W_CAM_IF`（默认 `GO2W_WIRED_IF`）修改。

本地调试：`dev/run.sh` 会启动 `dev/fake_camera.py`，循环回放真机录的 10 s 样本 `dev/camera_sample.rtp`。测试：`dev/test_camera.py`（拆帧，装了 ffprobe 会独立解码核对），`dev/test_camera_ws.py`（协议，要先运行 run.sh）。

## 地图续建（11-17）

建图流程里的「续建已有地图」：在已有地图上继续采集，把新区域并进同一张图。只能加不能删——挪走的家具留下的旧墙线擦不掉，要刷新只能重建。完整方案在主仓库 `docs/地图续建.md`。

流程：选基准 → 检查基准（`cont_preflight`）→ 开始续建（`cont_start`）→ 自检（`cont_check`）→ 收工（`cont_finish`）。

- 基准图必须有 `.posegraph` + `.data`。续建永远另存新名字，基准图不动；收工时写 `<name>.meta.json`，`routes.json` 里指向基准的任务改指新图（坐标系不变，站点不用重标）。
- 开始续建：起点位姿按 停车点（`data/parkings.json`）→ 自动定位（在磁盘上的基准图上做）→ 手动 的顺序取，起点必须在基准图范围内；然后关扫描闸门、调 `/slam_toolbox/deserialize_map`（`START_AT_GIVEN_POSE`），只放一帧验证扫描，自检通过才恢复连续采集（v1.0.5 起，见下面「续建扫描闸门」）。
- 这个服务读文件失败也返回成功，所以**自检是唯一判据**，没通过不许存图。自检（11-17 起不用回起点）用 slam 当前位姿（TF `map→base_footprint`，还没有 map 坐标系时退回起点位姿），角度修正绕该位姿转（`--pivot`），超出 0.40 m / 8° 报「起点位姿偏了」，并把修正量换算成起点位姿（`start_fix`）供重来；贴合率 < 85% 报「环境和图对不上」，提示站到能看到旧墙的地方。
- 检查基准时核对运控策略（环境变量或 `runtime.env` 的 `GO2W_CONTROL_POLICY`）和切片高度（`pcl2scan_slam.yaml`，运行镜像里在 `/opt/go2w/base/go2w_bringup/share/go2w_bringup/config`），和基准 `meta.json` 不一致就拦下。

测试：`dev/test_map_overlap_check.py`、`dev/test_mapmeta.py`、`dev/test_mapcontinue.py`（不用起 run.sh）。

## 站起与实际姿态（v1.5.1）

运控返回的 `ready` 只说明状态机插值完成。网页现在还会核对域 0 `/lowstate` 中的实测关节和机身倾角：在当前运控配置的 12 个站姿关节目标附近持续收到新反馈，才确认站起。FixStand 未实际到位时不启动策略；策略启动后再次确认，失败不增加站起计数，也不让出发流程继续。0% 电量、无反馈或读不到当前运控配置时拒绝发送新的站起请求。界面显示「未确认站起」和检查提示，指令回复成功不会改变实测姿态。

站姿目标读取 supervisor 管理的实际 `go2w_ctrl` 进程的 `--config`，因此跟随独立运控版本或自定义配置，不猜测内置默认路径。关节容差为 0.45 rad，实测采样须覆盖至少 0.3 s、相邻采样间隔不超过 0.5 s；这些是保守的软件确认条件，不代表接触地面或承重测量，需要上机核对正常站起和各策略。

正常 Velocity 行走允许关节偏离静态站姿：只有已根据连续实测取得确认的同一控制状态，才可沿用确认；此时界面显示「策略运行」。控制状态、序号、进程、配置变化，反馈过期、明确趴姿或异常倾角都会使旧确认失效。即使没有页面或任务检查，也会记录这些失效事件。读取配置期间发生急停、取消或并发站起时会重新检查，不再继续发请求。

本地测试：`python -m unittest dev.test_robot_feedback dev.test_taught_prepare -q`；`python -m unittest dev.test_live_health_integration -v` 启动真实网页后端和隔离假机器人，验证无导航反馈、正常站起、状态机虚报就绪和反馈中断；`dev/test_live_health_browser.py` 用 Chrome 检查无导航展示、状态卡片不被裁剪、0% 电量、指令回复不替代实际姿态、过期和断线清理。以上不启动真机动作。

## 运控策略切换（11-17）

## 电机温度（11-17）

后端直接旁听域 0 的 `/lowstate`，raw 回调最多每秒解析 5 帧，不依赖导航进程转发。按 CDR 偏移读电量和 16 个 `motor_state[i].temperature`（int8，℃，字节 `4 + 108 + 48·i`；0–11 是 右前 / 左前 / 右后 / 左后 × 髋 / 大腿 / 小腿，12–15 是轮子），状态里发 `motorTemp`，1.5 s 没收到反馈时显示未知。偏移用真机录包核对过：髋关节平时 46–67 ℃（低电量跑久了到过 81 ℃），大腿 / 小腿约 30 ℃，轮子约 23 ℃。

机器人卡片里「电机温度」一行显示最热的电机，点开是 4×4 的表。≥65 ℃ 黄、≥85 ℃ 红，并在地图上方提醒（只提醒，不拦出发）；阈值在 `static/js/util.js` 的 `MOTOR_WARN` / `MOTOR_CRIT`，是按实测定的保守值，不是宇树的保护温度。本地：`?mock&hot` 或 `GO2W_FAKE_MOTOR_TEMP=52,88,…（16 个）dev/run.sh` 看过热效果。

表上面的下拉（同 app「狗腿信息」）切换 **温度 / 错误标志 / 力矩**。错误标志读同一帧的 `motor_state[i].reserve[0]`（uint32，字节 `4 + 116 + 48·i`），状态里发 `motorInfo: {err: [16 个]}`；0 = 正常，非 0 标红显示十六进制，机器人卡片那一行变红写「N 个报错」（不进地图上方提醒）。用录包核对过：16 个电机平时全程 0；`reserve[1]` 一直是 507/508，不是错误码，不读。本地：`?mock&err` 或 `GO2W_FAKE_MOTOR_ERR=0,4,…（16 个）dev/run.sh`。

**力矩**读同一帧的 `motor_state[i].tau_est`（float32，N·m，电机估计值，字节 `4 + 92 + 48·i`），状态里在 `motorInfo.tau`；显示带正负（= 方向）、一位小数，|τ| < 0.5 变灰，不设报警线（不知道 Go2W 各关节的力矩上限）。录包核对：站着时小腿约 +7、左右髋符号相反（±4~7），轮子 ±2 以内。电量、温度、关节和力矩统一按最多 5 Hz 解析，状态按 2 Hz 推送；旧页面的 `motor_fast` 请求继续兼容。

**过热自动趴下（11-18）**：16 个电机（12 个腿关节 + 4 个轮子）任何一个 ≥68 ℃，而狗站着（FixStand / Velocity），后端就自动趴下：和手动「趴下」同一流程（先取消任务、上锁、等停稳），不管有没有「保持站立」或任务；失败每 5 s 重试。还在 68 ℃ 以上时不让站起。网页提醒变成「电机过热，已自动趴下」。阈值 `go2w_web.py` 的 `MOTOR_HOT_LIE`，环境变量 `GO2W_MOTOR_HOT_LIE` 可改，0 = 关掉；状态里 `ctrl.hotLie` 是当前阈值。温度按最多 5 Hz 更新，反馈过期时不沿用旧温度进行判断。本地：`GO2W_FAKE_MOTOR_TEMP=49,70,…（16 个）dev/run.sh`。

v1.5.1 起，导航、定位、建图都未运行时也可以读取电量和电机状态。机器人关机、反馈断开或过期时显示 `--`，0% 保留为有效电量读数。CPU/内存使用独立基础状态推送，不受地图、TF 或导航状态生成失败影响；网页后端断线时清除旧值。

这一块 4 Hz 重绘，只在内容变了才改 DOM——下拉框展开时改它的选项或选中值，Chrome 会重建弹出列表，闪个不停（策略下拉框同理）。

## 地图编辑（v1.0.2，11-18）

地图工具栏「编辑」（快捷键 6）打开编辑面板，编辑的是当前显示的、已经保存在 `data/maps` 里的地图；建图运行时不能编辑（地图还在变）。

- **去噪**：找孤立的小障碍块（8 邻域连通，格数 ≤ 滑块值，默认 4 格 = 10×10 cm 以内），先在地图上标红，点「去掉」才改。每块看周围一圈：空地多就擦成空地，未知多就擦成未知（射线尽头、楼外的零星点）。lab_20261116_c1 上 4 格能找到 479 块 / 726 格。

- **裁剪**：拖一个框，框外全部变成未知，用来去掉伸到楼外的射线。
- 撤销 / 重做（Ctrl/⌘+Z、Ctrl/⌘+Shift+Z，最多 40 步）、「按住看原图」。

保存只能**另存为新地图**（默认 `原名_e1`，同名拒绝），原图不动。网页只发「改了哪些格」（`[起点, 长度, 新值]` 段，下标按 OccupancyGrid 平铺）和它编辑时那张图的 CRC32；后端 `server/mapedit.py` 用硬盘上的原图算 CRC，对上了才改，只改动到的像素（254 / 0 / 205，按这张图的阈值和 negate 核对），其余字节和 yaml 照抄（只换 `image:`），写完按 map_server 规则读回来逐格核对。新图带 `meta.json`：`tool: web-edit`、`parent`、改了几格、去噪 / 画笔 / 裁剪次数、网页版本。可选把原图上的任务改到新图（有任务正在执行时不改）、保存后直接切换过去（导航在跑时会取消导航，切换后要重新定位）。

编辑后的图没有 slam_toolbox 的 `.posegraph` / `.data`，**不能当续建基准**：续建前置检查会提示用原图续建；续建一张有编辑版本的原图时提醒「编辑不会带到新图上，续建完要重新编辑」。

测试：`python3 dev/test_map_edit.py [真实地图.yaml]`（往返、只改动到的像素、CRC / 尺寸不对拒绝、不覆盖、negate 图、续建提示）。

## 雷达无数据提醒（v1.0.8，11-19）

起因：11-19 .21 雷达掉线（没上电 / 网线）一个多小时，`web.log` 里只有「里程计不可用」「拒绝解锁」这种间接痕迹；网页上「没有激光数据」红条只在浏览器里算，关掉页面就没了记录。

- 后端 `lidar_watch()` 每秒一次：建图 / 定位 / 导航在 run 且已稳 `GO2W_LIDAR_GRACE`（15 s）后，`/scan` 连续 `GO2W_LIDAR_STALE`（5 s）没数据 → `web.log` ERROR + 持续异常「雷达无数据」（`lidar_lost`，不存回溯包：包里也没点云）。

- 数据恢复 → INFO「雷达已恢复（断了约 N 秒）」并结束异常；断着时停档位 → 异常收掉。断着期间不重复刷日志。

测试：`dev/test_lidar_watch.mjs`（准备见文件头：用 `GO2W_LIDAR_CONFIG` / `GO2W_LIDAR_ARP` 伪造雷达配置和 ARP 表，`GO2W_FAKE_SCAN_OFF` 断激光）。

## 任务接续（v1.1.10，11-24）

任务没跑完就停了（某站 Nav2 到不了、手动取消、急停、断线上锁、切换档位、网页服务重启或断电），后端记一个**断点**：停在去第几站的路上、第几圈、已完成几站、停下的位置和原因。存在 `data/route_resume.json`（每个任务一个），每站出发前都会刷新，所以服务突然停掉也知道跑到了哪里（重启后标成「中断」）。

- 网页：「导航任务」下面出现「上次没跑完」框（各站已完成 / 下一站 / 未到），按钮「继续任务」= 照常站起、启动导航、定位，然后从没到的那一站接着跑完剩下的站，循环任务圈数接着算；「跳过，从第 N 站继续」= 那一站确实到不了时用。有断点时原来的「出发」变成「从头出发」（先确认，断点作废）。
- 断点不会自己执行、不自动重试。任务跑完、从头出发、任务被删、站点坐标 / 朝向改过（只改名字、备注、速度不算）或超过 24 小时（`ROUTE_RESUME_MAX_AGE`）就作废。
- 「终止任务」会清除所选任务的未完成进度，保留已保存的路线和运行参数。正在执行的任务须先取消导航，才能终止接续。清除进度写盘失败时保留原断点并提示重试；操作不会取消其他任务。
- 协议：`routes[].resume`（没有是 `null`）、`task.resumed / resumable`；下发时 `route_start` 带 `resume: "continue" | "skip"`，接续时圈数用断点里的。云端字段说明在主仓库 `docs/巡逻监控接口_v1.1.10新增.md`。

站点限速协议为可选的 `points[].vmax`；缺失时动态继承任务上限。`route_terminate` 携带 `route_id`，成功后广播更新的 `routes[].resume = null`。

测试：`dev/test_route_resume.mjs`。

## 连续通过、站点停留（v1.1.11，11-24）

起因：1–2 m 一站、拐角 22–46° 的小圈，原来每站一个 NavigateToPose，几乎每站都减速 → 原地转 → 再起步（DDS 黑匣子实测每站约 2.5 s，一圈多 18 s）。

- **连续通过**（任务运行参数 `opts.through`，默认开）：以设了停留的站为界把路线切成几段，每段一个 **NavigateThroughPoses**，Nav2 一次规划经过这段所有站的连续路径，中间站不减速不停车；停留站和终点照常停稳、对准站点朝向。离站 0.5 m 以内（`ROUTE_THROUGH_PASS`）或 Nav2 已经划掉就算经过，进度、日志「经过第 N 站」、断点照旧。一段最多 30 站（`ROUTE_SEG_MAX`）。日志记每段「多点规划用时」。
- 行为树用本仓库的 `server/bt/navigate_through_go2w.xml`，下发时放进 `goal.behavior_tree`（网页包在容器里路径不变，bt_navigator 直接读，不用改导航镜像）：恢复动作同 `navigate_go2w.xml`（倒车 0.6 m / 0.15 m/s，默认树 0.05 m/s 的倒车 Go2W 不执行）；`RemovePassedGoals` 单独放在最前面每轮都跑（默认树里它跟着 0.333 Hz 的重新规划，可能刚好没判到经过的站，下一次规划就掉头回去找）。v1.1.12 起途中 10 秒才重新规划一次（`RateController hz="0.1"`，原来 1 Hz）：一段是一次规划好的，每秒重算时人走过后全局代价地图里的拖尾会让路径来回摆、看着像追人；出发和每次恢复后都会先立刻规划，途中新障碍由 MPPI 局部绕。清全局代价地图节点 `server_timeout` 1000 ms（默认 20 ms 清不完，每次都判失败）。
- 导航没有 `navigate_through_poses` 服务、行为树文件不在、或者多点目标一开始就失败（< 5 s 没有任何反馈，多半是行为树没加载上）→ 这次自动退回一站一站走，日志说明。运行参数里关掉「连续通过」也是一站一站走。
- **站点停留**：每站可以填停留秒数（1–3600，`points[].dwell`，0 不存）。到站停稳、转到站点朝向后原地等够再走，任务卡片「停留中 · 还剩 N s」（`task.phase = dwell`、`dwellLeft`）。停留中取消，断点记在这一站，继续时回来重新停够。地图上停留站画成**橙色**并标「停 N s」，直接经过的站黄色，终点绿色。
- 一站一站走时：拐角 ≤ 60°（`ROUTE_PASS_TURN`，原来 29°）的站不停车，提前切到下一站；配合导航参数 `angular_dist_threshold` 0.9（导航镜像 PR，没发版前狗上 `sudo bash ~/nav_tune/shim_turn.sh 0.9`），否则 RotationShim 还是会原地转。
- **假到达**：Nav2 报到达，但狗离站点超过 0.5 m（`ROUTE_FAKE_ARRIVE`），或连续通过时中间还有站没经过 → 不算，从第一个没经过的站重新出发；连续 3 次判失败。起因：提前换站后 Nav2 有时 0.7 s 就报下一站到达，狗其实还差 ~0.9 m（11 站小圈 6 趟里 4 趟第 10 站被跳过）。
- **终点就在出发位置**（v1.1.13）：控制器的 goal checker 只看路径终点，一段的终点离狗 ≤ 0.6 m（`ROUTE_THROUGH_NEAR_END`，环线回到起点）时 Nav2 会当场报到达、中间站一个没走。现在先只跑到它前一站，终点那站下一段单独发。
- 假机器人：`dev/fake_ros` 支持 NavigateThroughPoses（经过半径 `GO2W_FAKE_THROUGH_RADIUS`）；`/tmp/go2w_fake_early_ok`（内容 = 次数）让接下来的导航目标 0.3 s 就报成功，测假到达。

测试：`dev/test_route_through.mjs`、`dev/test_route_dwell.mjs`；`dev/test_routes.mjs` 测一站一站走（任务带 `through: false`）。

## 地图显示方向

建图时地图的 x 轴取机器人开始建图那一刻的朝向，所以有的图是斜的、有的是竖的。这不影响定位和导航（Theta* 能走任意角度的直线），只是看着别扭。网页可以按地图单独保存一个**显示方向**：只转画面，不改地图坐标，所以路线、巡逻点、初始位姿都不用重做。

- **自由旋转：** 按住 Shift 拖动地图，或按住右键拖动，地图绕画面中心转。靠近 0° / 90° / 180° / 270°（±3°）会自动吸附，按住 Alt 不吸附。
- **指南针按钮：** 在地图右上角，红色针尖指向地图坐标的 +y 方向。单击顺时针转 90°，双击复位到 0°。
- **精确对齐：** 在「地图与录包」面板点「沿墙选两点」，选同一段长直墙上的两个点（至少 0.5 m，推荐 1 m 以上），可切换「对齐水平 / 对齐竖直」；「复位方向」回到 0°。
- **保存：** 松开鼠标后存到扩展坞的 `data/map_views.json`，按地图名记录，0° 不记录。从 166 和 142 打开、换哪台电脑看到的都一样，有人改了其他网页会跟着变。切换地图时自动换成那张图的方向，断线重连、切换档位不会清除。
- **建图时：** 还没有地图名，方向先暂存在 `_mapping` 下。「保存当前地图」时带给新地图。
- 地图、机器人、点云、路线、目标一起旋转，背景网格保持水平；鼠标点击换算回地图坐标，位姿读数仍是地图坐标。键盘遥控 W/S/A/D 相对机器人本身，不受影响。

**导出对齐地图（一般不需要）：** 建图运行时，输入新地图名并点击「保存对齐地图」。后端先保存原图及 SLAM 数据，再按当前显示方向把图片转正，生成 `<名字>_aligned.pgm/.yaml/.png`，都位于扩展坞的 `~/go2w/data/maps`。图片最多转 ±90°，剩下的 180° 记成新地图的显示方向。对齐副本的坐标和原图不同：用它导航要重新设置初始位姿、重新选路线站点。原图保留用于续建。导出失败时原图保留，可以重试；已有文件不会被覆盖。只在需要地图文件本身是正的时候才用（比如给 RViz 或别的工具）。

`dev/test_map_alignment.py` 验证图片旋转、原点和未知区域；本地假 ROS 页面也会运行相同的导出程序，可在未连接机器狗时检查保存结果。

### P1 的安全规则

- **急停**：取消所有导航目标（包括 RViz、patrol 发的）并调用 `/go2w_cmd_bridge/arm(false)`，cmd_bridge 会立即发 StopMove 并上锁。急停是锁存的：解除之前拒绝解锁和发目标；急停期间如果底盘被别处（比如 `nav.sh arm`）解锁，后端会再次上锁。解除急停后底盘仍保持上锁。
- **心跳**：网页每 0.5 s 发一次心跳（放在 Web Worker 里，切换浏览器标签页不会误触发）。最近一个发过运动相关指令（解锁、目标、取消、急停）的网页是「控制方」。控制方心跳超过 1.0 s 或网页关闭时，如果底盘解锁着或有导航目标，后端会取消导航并上锁，恢复后也不会自动解锁。超时时间用后端参数 `--heartbeat` 调整。
- 后端（`go2w_web` 容器）本身挂掉时没有人替它上锁：Nav2 和 cmd_bridge 会照常运行，这时请用遥控器。
- 暂停在真机上不支持（Nav2 没有暂停），用取消或上锁代替。

## 回溯录制

**自动包名称（v1.3.2）**：导航失败为 `<狗编号>_navfail_MMDD_HHMMSS`，长时受阻为 `<狗编号>_longstop_MMDD_HHMMSS`；两类异常合并到同一个自动包时为 `<狗编号>_longstop_navfail_MMDD_HHMMSS`。其他自动异常暂沿用原名称，手动录制继续带 `_trigger_`。长狗编号按现有规则缩短并加摘要，整个名称不超过48字符；旧包不改名。异常自动包仍按异常时刻采集前15秒＋后15秒，与手动点击前20秒＋后10秒分别保存。

**压缩（v1.3.1）**：持续录制和 Python/C++ 回溯录制的新包使用 MCAP 内部 Zstd 快速档，保留数据块 CRC、消息索引及摘要，可直接回放和索引读取。共享配置为 `tools/mcap_writer.yaml`，需与录制脚本及 C++ 可执行文件一同发布；缺失时明确报错，不静默生成未压缩包。旧包不自动转换。回溯内存缓存仍保存原始序列化数据，压缩发生在写包时，不改变缓存窗口或内存上限。

一键上传使用 rsync Zstd 1 级传输压缩（发送端、接收端均需支持 Zstd；当前运行镜像 rsync 3.2.7、接收服务器 3.4.1 已核对支持）。它减少传输流量，接收端仍是原 bag 目录，语音与匹配文件不变；仅传输压缩不会缩小旧包的磁盘占用。新 MCAP 已压缩时，传输压缩的额外收益可能较小。

真实 ROS 软件回归：在已具备 ROS Humble 与 C++ 编译依赖的隔离容器内运行 `python3 -m unittest dev.test_mcap_compression`，核对 Python 持续/回溯及 C++ 写入的 Zstd、CRC、索引、消息内容、时间戳和缺失配置错误。x86/ARM 软件检查不代替 Orin 上的录制负载验收。

部署后，新启动的录制进程才加载新版写入器。已运行的持续录制需停止后重新开始；回溯录制需关闭再打开，并等待缓存重新积累。独立 Web 更新只重启 Web，不会自动打断正在录制的进程。Web 源码包缺少 C++ 可执行文件时仍沿用原有 Python 回退，同样启用压缩；单独构建 C++ 时 `build.sh` 会将共享配置一同复制到可执行文件旁。

录制快捷键：**Shift+R** 切换开始/停止持续录制，**Shift+Enter** 录制当前数据。鼠标悬停在对应按钮上可查看快捷键；输入文字、输入法组合和长按时不触发。

包名前缀是**狗编号**（11-12 起；下面写的 `go2w_` 是更早的叫法），比如 `go2w-01_1118_101500`。11-24（v1.1.11）起人在网页上主动录的包带 `_trigger_`：「开始录包」和「保存刚才 20 秒」存成 `go2w-01_trigger_<月日>_<时分秒>`，自动异常包按上面的原因标签命名；其他自动类型暂保留 `go2w-01_<月日>_<时分秒>`。11-18 起狗编号按这个顺序取：狗硬盘上的 `/opt/go2w/config/runtime.env`（容器里 `/etc/go2w/runtime.env`）里的 `GO2W_ROBOT_ID` → 进程环境变量 `GO2W_ROBOT_ID` → 默认 `go2w-01`。每只狗在自己的 runtime.env 里写，不放进镜像或网页包；每次录包时现读，改了不用重启。格式：字母或数字开头，只能有字母、数字、`_`、`-`，最多 30 个字符，写错了用默认值并在启动日志里说明。启动日志会打「狗编号 go2w-01（来自 …）」。后端代码里用 `robot_id()` 取。

网页「开始持续录制」是分段录制（主仓库的 `scripts/segment_recorder.py`，替代原来的 `ros2 bag record`）：一直录，每 30 秒存成一个独立的包，包名是这一段的开始时间 `go2w_<月日>_<时分秒>`（同一秒重名加 `_2`；11-12 前是 `web_`）。每一段开头都写入 `/map`、`/tf_static`、`/robot_description` 这种只发一次的 topic，任何一段单独拿出来都能回放；段与段之间不丢消息。正在写的那段在 `data/bags/.recording/`，写完才整体移进 `data/bags`，所以列表里的包都能直接上传、删除。停止录包时把当前这段写完再退出。上次异常退出没写完的段会被移成 `<名字>_unfinished`（缺 metadata.yaml，用 `ros2 bag reindex` 修复）。段长在 `procs.py` 的 `BAG_SEGMENT`；日志 `data/logs/bag_go2w_<时间>.log`。命令行 `nav.sh` 手动跑的 `ros2 bag record` 仍按一个包处理。

录包区的「回溯录制」打开时（默认打开），建图 / 定位 / 导航运行期间，回溯进程将数据留在内存循环覆盖。点击「录制当前数据」或按 **Shift+Enter**，后端收集后10秒再将固定窗口写入 `data/bags/<狗编号>_trigger_<时间>_r`；手机短暂断线不会取消后端保存。过长的狗编号在文件名中使用短摘要以满足48字符限制，`capture.json` 保留完整狗编号。快捷键在输入框、文字编辑区和对话框里不触发，连续误触只保存一包。回溯缓存为35秒（含轮询余量），内存字节上限仍生效；刚启动、重启或缓存不足时可能少于30秒，界面显示实际时长。所有 topic 默认录制；`/map`、`/tf_static`、`/robot_description` 等只发一次的话题保留在包头。可以和普通分段录包同时运行。日志在 `data/logs/rollback.log`，开关状态在 `data/rollback.json`。

**语音备注与手机录制页（11-24）**：保存数据的同时，使用当前电脑或手机麦克风录制语音，默认5秒，可设1–20秒，设置记在本机浏览器。回溯开关、语音时长和手机录制页入口位于录包卡片底部默认收起的「更多设置」。第一次需允许麦克风权限；等待授权不改变数据窗口。打开同一服务的 **`/record`**（控制台录包区有「手机录制页」链接），只显示录包结果和录制控件，底部中央圆形按钮按一次保存一包。结果列表可播放随包保存的语音。音频为浏览器支持的 WebM/MP4/Ogg，保存在包目录 `voice-note.audio`，`voice-note.json` 保存时长；`capture.json` 保存数据窗口。暂时离开页面会提前结束语音；上传失败可在页面重试或下载本地音频，结束处理后才能开始下一包。录音失败仍保存数据，不能把「数据包已保存」当作「语音也已保存」。

**一键上传会把数据、录音和匹配信息一起上传。** 当前运行配置的目标是 `evoengine@192.168.1.166`，接收目录为 `/home/evoengine/go2w_bags/<包名>/`（上传密钥由 rrsync 限制在 `go2w_bags` 下；`GO2W_UPLOAD_DEST` 可覆盖连接目标）。上传整个包目录，包括 MCAP/DB3、`metadata.yaml`、`capture.json`、`voice-note.audio`、`voice-note.json` 和 `recording-link.json`，不会把音频单独扔进公共目录。`recording-link.json` 明确列出包名、数据文件、同一次保存的记录编号（`request_id`）、录音文件、时长和录音SHA256；`voice-note.json` 也包含包名和记录编号，拆开文件后仍可匹配。

**多选上传（v1.4.0）。** 展开已录制列表，可逐个勾选或全选后点击「上传所选」，也可以在上传期间继续点击其他包的上传按钮。同时执行两个包（包括等待语音阶段），更多包按提交顺序排队，各包分别显示排队、进度和结果；某个包失败不会阻断其他包。排队和上传期间禁止重复提交同一个包或删除该包。队列保存在当前服务内存中，重启后未完成的包需要重新提交。

接收端使用 `rrsync` 时，上传密钥的强制命令须包含 `-no-lock`，例如 `/usr/bin/rrsync -wo -no-del -no-lock /home/evoengine/go2w_bags`；否则默认的整个目录单写锁会使第二个并发上传立即失败。保留密钥的 `restrict`、`-wo`、`-no-del` 和固定目录限制。`.166` 已为两只狗的上传密钥启用此选项，详见[修复与实机验证记录](docs/development/2026-11-25-concurrent-bag-upload.md)。

**重复包（v1.4.4）。** 已有有效上传回执的包直接显示「已上传」，全选和批量上传会跳过它。点击该行的核对按钮并确认「核对并补齐」，才会检查服务器缺失或变化的文件，仍使用原目录，不新增同名副本。回执绑定上传目标和本地包文件的大小/修改时间；数据、录音或目标变化后重新核对，未记录这些信息的旧版回执需核对一次。同一个目录名代表同一录包，不自动合并名称不同的手动包和异常自动包。

**录音回放（v1.4.1）。** 已录制的包旁显示录音状态和播放按钮；有录音时可播放、暂停，并在原生播放器中调整进度和音量。播放器独立于列表，上传进度刷新不会中断播放；音频只在点击后加载。无录音或录音待保存的包不会启用播放，鼠标悬停可查看已记录的原因。手机 `/record` 结果列表也可直接播放已保存的语音备注。

提前点上传时会显示「等语音」，最多等45秒，录音保存后自动继续，无需再次点击。语音一直未保存时，上传失败且不标为已上传；浏览器确认没有麦克风权限或用户结束语音处理时，匹配文件明确记录「无录音」和原因，再上传可用数据。实际传输期间锁定本包的语音文件，避免扫描目录时遗漏；已上传后又新增语音会改成「待核对」，核对整包即可补齐。旧的无录音数据包仍可上传，匹配文件标记 `not_recorded`。

手机录制页面意外关闭后，重新打开 `/record`，待处理包会显示「结束待处理语音」，可明确确认本包无录音再继续上传。语音写入、状态更新与断线恢复均核对记录编号，不能将旧页面的语音绑定到同名新包。上传前对照 `metadata.yaml` 检查所有声明的数据分片；旧版上传回执若不能证明录音也已上传，会显示「待核对」，不会据此自动清理本地唯一录音。

**手机通过局域网访问时，麦克风需要受信任的 HTTPS。** 直接打开 `http://<狗的局域网地址>:8080/record` 可以录数据包，浏览器会禁止麦克风。服务已支持 `--tls-cert <证书文件> --tls-key <私钥文件>`，例如在原启动命令中添加这两个参数，并使用 `https://<证书包含的地址>:<服务端口>/record` 访问；也可由现有 HTTPS 反向代理转发 `/record`、`/api/recordings`、`/ws` 和静态资源。证书须包含实际访问的IP或域名，签发机构须由手机信任；只跳过自签名证书警告不保证麦克风可用。相应证书、代理与手机信任配置需在部署环境完成。本次未远端部署或修改手机信任设置。

卡住自动保存：回溯录制在跑时，如果导航目标还没结束（没到、没取消）、底盘已解锁、没急停，而 odom 位置 8 秒内移动不到 8 cm、朝向变化不到 0.15 rad（约 9°），就认为狗卡住了，网页日志报一条警告，再等15秒，保存判定时刻前15秒＋后15秒的数据。异常自动保存保持原规则，与手动保存重叠时有界等待其采集和写盘完成；实际覆盖仍受缓存和字节上限限制。同一次停住只存一个；两次自动保存至少隔60秒。阈值在 `go2w_web.py` 的 `STUCK_*`，等待秒数也可以用环境变量 `GO2W_STUCK_SECONDS` 改。升级需同步更新前后端与 Python/C++ 回溯进程，以支持固定结束时刻的请求协议。

### 站点强制跨越

在导航任务的每个站点勾选“强制跨越”：可以全部不选；启用时至少选择两个点。系统按路线顺序确定一个区间，到达第一个选中点后设置 `false`，到达最后一个选中点后设置 `true`。首尾之间没有勾选的站点也属于这个区间；选择多个点不会生成多个独立区间。只选一个点时不能确认、保存或出发。

配置以 `points[].forceCrossing: true` 随任务保存，未勾选不存字段，旧任务无需修改配置；从头出发时也初始化正常避障。排序、改位置和修改站名会保留该站的配置；删除、重排后按新顺序重新计算首尾点。改变配置后，旧断点不能继续使用。

执行由后端负责。**从头启动任务时，先成功设置 `FollowPath.ObstaclesCritic.enabled=true`，再导航到起点；未勾选强制跨越的任务同样执行这一步。** 初始化失败会终止本次任务并尝试恢复，初始化期间取消不会继续下发目标。已经在起点0.5米范围内时，也先完成初始化，再执行起点的跨越配置。逐站行驶和连续通过都在首尾边界按站点指定朝向完成到点确认后设置参数，等待命令成功再发下一段；连续通过会在边界处分段，区间内部仍使用原有通过规则。循环每圈启闭；终点返回起点保持正常避障（`true`），速度上限仍沿用任务设置。若起点也是首个选中站，下一圈到达起点后再设置 `false`；最后回到起点结束任务时不会重新开启。断点继续或跳过后，如果下一个目标在区间内，则先重新开启再出发。

任务取消、失败或参数设置失败时停止后续导航，并尝试恢复 `true`；恢复失败会写入任务信息和错误日志，同一服务进程的下一次任务必须先成功恢复才能出发。突然断电或进程被强杀时无法保证执行恢复，重启后应先核对机器人上的实际参数。

恢复失败后，普通单点目标也会被拒绝。多点任务下次启动时自动尝试恢复；也可以调用下方的 `true` HTTP 入口，成功后解除单点目标的拦截。ROS 明确返回 `Setting parameter failed` 时，即使命令退出码为 0，也会返回 HTTP 502 并停止任务，不把节点拒绝当作成功。

两个原有 HTTP 入口仍为无请求体的 `POST /api/obstacles-critic/true` 与 `POST /api/obstacles-critic/false`。HTTP 与路线复用同一个异步设置服务，参数命令串行执行；配置了强制跨越的任务执行期间，手动 HTTP 写入返回 409，避免覆盖任务设置。“强制跨越”开启时，`FollowPath.ObstaclesCritic.enabled` 和 `voxel_layer.enabled` 都设为 `false`；退出跨越、取消或失败时都恢复为 `true`。HTTP 地址中的 true/false 直接对应该 ROS 参数值。成功响应中的 `parameters` 列出两个参数的命令执行结果；实机可分别用 `ros2 param get /controller_server FollowPath.ObstaclesCritic.enabled` 和 `ros2 param get /global_costmap/global_costmap voxel_layer.enabled` 核对实际值。
